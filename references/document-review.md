# 法律文书检查与修订规范

审查合同、诉状、答辩状、判决书或其他法律文书时，找出能够根据原文或已核验法条确认的问题。输出聚焦具体错误和可执行修改；符合本页标准的 AI 味表述统一作为“AI味问题”提示。

## 一、工作流程

1. **准备待审查文书文本**：
   - 将待审查的文书正文保存为临时目录下的 UTF-8 文本文件（例如 `$TMPDIR/input_doc.txt`）。
2. **运行本地自动化规则检查 (`prepare`)**：
   - 调用 `scripts/xunfa.py prepare --text-file "<UTF-8临时文本>" --output "<临时目录>/review-context.json"`。
   - 取得文书的 `text`、`ruleIssues`（自动检出的身份证号校验错误、统一社会信用代码校验错误、手机号/银行卡号格式错误、非法日期、未替换占位符、常见错别字、未配对标点符号）和 `textSha256`。
3. **全文人工/深度审查**：
   - 阅读全文，确认脚本提示的 `ruleIssues`，并补充明确的事实矛盾、数值计算错误、序号断层、法条引用错误、逻辑漏洞和“AI味问题”。
   - 当收到“检查错误”指令时，优先直接列出错误点，不提及正确点。
4. **法条核验**：
   - 仅针对原文中明确出现的法条进行核验（合同、协议等书名号内容不作为法条）。不得臆造原文未出现的法条；无法确认的引用标为“未核实”。
5. **交付检查报告**：
   - 按规范格式交付全部问题和未核实项后，询问用户是否按列出的建议输出完整修订文本。
6. **精确生成修正版 (`apply`)**：
   - 只有用户确认的项目才写入 `accepted-issues.json` 并运行 `apply` 命令，确保确认替换范围以外的内容 100% 原样保留。

## 二、本地命令调用

```bash
# 1. 生成检查上下文与规则问题
python scripts/xunfa.py prepare --text-file "<UTF-8临时文本路径>" --output "<临时目录>/review-context.json"

# 2. 根据用户确认项生成零篡改修正版
python scripts/xunfa.py apply --context "<临时目录>/review-context.json" --document-number 1 --issues "<临时目录>/accepted-issues.json" --output "<输出路径>/修改后完整版本.txt"
```

## 三、四大检查重点

1. **法条**：核对法名、条号、正文、版本和适用条件。仅核查原文中明确出现的法条；引用现行法时必须采用现行有效版本。合同、协议等书名号内容不作为法条。
2. **文字与结构**：检查明确的错别字、病句、未配对标点（`（）`、`《》`、`“”`、`‘’`）、必要栏目缺失、序号断层和交叉引用错误、未替换模板占位符。
3. **事实与数值**：
   - 校验 18 位身份证号（地区码、出生日期、顺序码、MOD 11-2 校验码）；
   - 校验 18 位统一社会信用代码（字符集、MOD 31 校验码）；
   - 校验手机号码、银行卡号格式及公历日期合法性；
   - 检查文书内部主体名称、日期、金额、数量、证据编号前后冲突，以及单价、合计、比例、利息和期间等可由已载明前提核算的数值关系。
4. **论述逻辑**：检查事实、法律依据、请求和结论之间的明确矛盾或缺口。材料不足以判断时，标为“待核实”并说明需要的材料。

## 四、“AI味问题”专项排查标准

全文检查时，以下情况统一标为“AI味问题”（其中核心词汇已内置于 `legal_review.py` 的 `prepare` 自动化扫描引擎中）：

1. **伪专业套话与大厂黑话（核心必查词库）**：
   - 虚假证据套话：`进一步印证`、`切断`、`证据链`、`完整证据链`、`形成完整证据链`、`至关重要`、`彻底落空`；
   - 商业与网络黑话：`闭环`、`资金闭环证据`、`逻辑闭环`、`印证闭环`、`一揽子`、`焊死`、`锁定事实`、`铁证如山`。
2. **结论先行+冒号总分结构**：结论性首句后使用冒号，再展开同一事实或理由的总分结构（例如：“双方借贷合意真实合法，内容清晰明确：原被告于……”）。优先只修改或删除结论性引导短句及冒号，后续事实内容不动。
3. **主观绝对化断言与情绪化修辞**：使用“显而易见、毋庸置疑、不言而喻”等主观断言代替客观事实论证，或使用“肆意、践踏、底线”等情绪化修辞。
4. **滥用总结词**：非结尾段使用“综上所述”，或全文重复使用“综上所述”。

**排查边界约束**：
- 不因单个词语出现就直接机械判定。引用法条原文、判决书原文、对方陈述、必要法律术语，或根据上下文确有具体指代含义的表述，不作为 AI味问题。
- 每项只列出最小必要的原文范围、简短原因和建议修改；**不跨段润色、不补充事实、不改写无关内容**。

## 五、问题报告交付格式

按普通数字编号列出问题，写明文书、类别、原文或位置、问题和建议修改：

```text
1. 《起诉状.docx》，错别字
原文：“权力人”
建议修改：“权利人”

2. 《起诉状.docx》，事实错误
问题：两处付款日期不一致（第一段为2025年3月1日，第三段为2025年5月1日）。
建议：根据付款凭证确认正确日期。

3. 《起诉状.docx》，AI味问题
原文：“双方借贷合意真实合法，内容清晰明确：”
问题：结论性引导语重复后文事实展开。
建议修改：删除该引导语，保留后续事实内容。
```

法条核验无果或材料不足时，单列“未核实项”说明原因。

## 六、生成修正版规范 (`apply`)

用户确认需要修订文本后，只将其明确确认的项目写入 `accepted-issues.json`。其中保留目标文书在 `review-context.json` 的 `documents[文书序号-1].textSha256`，并为每项填写 `apply`、`replacementStatus`、字符偏移位置（`start`、`end`）、`original` 和 `replacement`。`replacementStatus` 必须为 `ready` 才能应用：

```json
{
  "textSha256": "<review-context.json 的 textSha256>",
  "issues": [
    {"apply": true, "replacementStatus": "ready", "start": 0, "end": 2, "original": "错字", "replacement": "正字"}
  ]
}
```

`apply` 会严格校验上下文 SHA-256 哈希、原文切片匹配和替换位置，拒绝任何重叠替换，再按“原文未修改片段 + 确认替换内容 + 原文未修改片段”生成完整修订文本。确认替换范围以外的内容 100% 原样输出；没有确定替换值或未获用户确认的问题，绝不擅自替换。
