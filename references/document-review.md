# 法律文书检查

审查合同、诉状、判决书或其他法律文书时，找出能够根据原文或已核验法条确认的问题。输出聚焦具体错误和可执行修改；符合本页标准的 AI 味表述统一作为“AI味问题”提示。本页的 `prepare` 已完成文书解析，文书检查直接使用本页流程。

## 工作流程

1. 同一案件的待审文书一次传入 `prepare`。文书包含法条引用或需要核验法律依据时，由 Agent 阅读原文、整理明确出现的法名和条号后运行一次 `laws`。
2. 用户粘贴文本时保存为当前任务私有临时 UTF-8 文件；用户提供文件时直接使用原文件。
3. 运行 `prepare` 取得每份文书的 `text`、`ruleIssues` 和 `textSha256`，以返回的文本作为检查依据。
4. 阅读全文，确认脚本提示的错别字、标点、日期、号码、占位符和结构问题，并补充明确的事实、数值、序号、论述和 AI 味问题。检查上下文较长时，按 `text` 和 `ruleIssues` 字段读取所需内容，避免一次读取整个 JSON。
5. 文书包含法条引用或需要核验法律依据时，Agent 仅根据原文中明确出现的法名和条号写入查询 JSON，再运行一次 `laws --queries` 批量核验。不得臆造原文未出现的法条；无法确认的引用标为未核实。
6. 交付全部问题和未核实项后，询问用户是否按列出的建议输出完整修订文本。只有用户确认的项目才运行 `apply`。

认证状态按[认证与安全](authentication.md)完成登录后重试原命令。`partial` 结果保留成功文书，并在结果中说明 `itemErrors`。检查上下文和结果文件放在当前任务私有临时目录。

## 命令

```bash
python scripts/xunfa.py prepare --files "<文件1绝对路径>" "<文件2绝对路径>" --output "<临时目录>/review-context.json"
python scripts/xunfa.py prepare --text-file "<UTF-8临时文本>" --output "<临时目录>/review-context.json"
python scripts/xunfa.py laws --queries "<临时目录>/law-queries.json" --output "<临时目录>/law-results.json"
```

每个法条查询包含 `lawName` 和 `articleNumber`。服务端结果用于核验法名、条号、原文和效力状态；是否适用于案件事实仍需结合材料判断，材料不足时作为未核实项说明。

## 检查重点

- 法条：核对法名、条号、正文、版本和适用条件。仅查询原文中明确出现的法条；引用现行法时采用名称精确且 `statusText=有效` 的检索结果。合同、协议等书名号内容不作为法条提交查询。
- 文字与结构：检查明确的错别字、病句、标点、必要栏目、序号和交叉引用错误。
- 事实与数值：检查文书内部可证明的主体、日期、金额、数量、证据编号冲突，以及单价、合计、比例、利息和期间等可由已载明前提核算的关系。
- 论述：检查事实、法律依据、请求和结论之间的明确矛盾或缺口。材料不足以判断时，标为待核实并说明需要的材料。

## AI味问题

全文检查时，以下情况统一标为“AI味问题”：

- 结论性首句后使用冒号，再展开同一事实或理由的总分结构。优先只修改结论性引导短句及冒号，后续事实内容不动。
- “进一步印证、切断、证据链、完整证据链、形成完整证据链、至关重要、彻底落空”，以及显而易见、毋庸置疑、不言而喻、无可辩驳、毫无疑问、任何、绝对、完全等绝对化断言。
- 践踏、肆意、底线、严重破坏市场秩序、于法不容等情绪化修辞；值得注意的是、不可否认的是、毋庸讳言、进而言之等模板化过渡；“该等”和机械使用的“且/并且”。
- 非结尾段使用“综上所述”，或全文重复使用“综上所述”。

不因单个词语出现就直接判定。引用法条、判决原文、对方陈述、必要法律术语，或根据上下文确有具体含义的表述不作为 AI味问题。每项只列出最小必要的原文范围、简短原因和建议修改；不跨段润色、不补充事实、不改写无关内容。

## 交付格式

按普通编号列出问题，并写明文书、类别、原文或位置、问题和建议修改。例如：

```text
1. 《起诉状.docx》，错别字
原文：“权力人”
建议修改：“权利人”

2. 《起诉状.docx》，事实错误
问题：两处付款日期不一致。
建议：根据付款凭证确认正确日期。

3. 《起诉状.docx》，AI味问题
原文：“双方借贷合意真实合法，内容清晰明确：”
问题：结论性引导语重复后文事实展开。
建议修改：删除该引导语，保留后续事实内容。
```

法条核验失败、解析失败或材料不足时，单列“未核实项”说明原因。未发现明确问题时，简要说明检查结果。列出全部问题后，询问用户是否按上述建议生成修订文本。

## 生成修正版

用户确认需要修订文本后，只将其明确确认的项目写入 `accepted-issues.json`。其中保留目标文书在 `review-context.json` 的 `documents[文书序号-1].textSha256`，并为每项填写 `apply`、`replacementStatus`、位置、原文和替换文本。`start` 和 `end` 是该文书 `text` 的字符偏移，`replacementStatus` 必须为 `ready` 才能应用：

```json
{
  "textSha256": "<review-context.json 的 textSha256>",
  "issues": [
    {"apply": true, "replacementStatus": "ready", "start": 0, "end": 2, "original": "错字", "replacement": "正字"}
  ]
}
```

```bash
python scripts/xunfa.py apply --context "<临时目录>/review-context.json" --document-number <文书序号> --issues "<临时目录>/accepted-issues.json" --output "<输出路径>/修改后完整版本.txt"
```

`apply` 会校验上下文哈希、原文和替换位置，并拒绝重叠替换，再按“原文未修改片段 + 确认替换内容 + 原文未修改片段”生成完整修订文本。因此，以 `prepare` 返回的 `text` 为基准，确认替换范围以外的内容原样输出。没有确定替换值或未获用户确认的问题，不生成替换。
